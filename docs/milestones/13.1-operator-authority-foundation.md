# Milestone 13.1: Operator Authority Foundation

## Objective

Introduce the human authority layer governing Project Intelligence:

```text
Base Project Intelligence + Operator Authority
                              ↓
                  Resolved Project Intelligence
```

The base report, its evidence, and its history remain unchanged. Resolved
understanding is the current operational interpretation, not a claim of
objective truth.

## Scope

- Typed annotations, acceptances, rejections, corrections, and disputes
- Stable local and named operator identities
- Human confidence and intent vocabularies
- Draft, active, superseded, retired, withdrawn, expired, review-required, and
  orphaned lifecycle states
- Project-scoped deterministic response and transaction IDs
- Committed transaction replay and immutable response revisions
- Pure resolved-intelligence and explanation projection
- Full-ID and unique rule-ID selectors
- Text and versioned JSON CLI output

Observed entities may be annotated but cannot be governed by acceptance,
rejection, correction, or dispute. Those responses require a derived insight.
Corrections reject one derived interpretation and activate a replacement
without changing the original.

## Domain and storage model

`astra-knowledge` owns response records and persistence. Response payloads are
typed rather than generic. Target bindings contain stable IDs, optional rule
IDs, classifications, statements, deterministic evidence fingerprints, and
related entity references. They contain no raw source, command output, diff,
environment value, credential, or absolute path.

Storage remains below the project knowledge namespace:

```text
projects/<project>/
  operator-responses/<response>/<transaction>.json
  transactions/<transaction>/manifest.json
  transactions/<transaction>/commit.json
  transactions/sequence.json
```

Only committed transactions are replayed. A prepared transaction has no
effect. Draft edits produce immutable revisions under one stable response ID;
draft deletion produces a tombstone. Active changes allocate a new response
and explicitly supersede the prior record.

## Resolution model

`astra-intelligence` consumes base intelligence and committed responses through
a pure resolver. It does not read storage. The version-2 resolved envelope
contains:

- resolution status;
- active response count;
- conflicts;
- untouched base intelligence;
- resolved interpretations;
- active annotations;
- optional explanations.

Acceptance preserves the base statement with accepted status. Rejection
preserves it as rejected. Correction emits the operator replacement as a
derived operational interpretation. Dispute leaves the target unresolved.
Multiple annotations may coexist. Only one active governing response may
control a target unless explicit supersession replaces it.

Evidence drift expires acceptance and state-bound annotations. It marks
rejection, correction, and dispute as review-required. Missing targets are
orphaned. Persistent annotation stays active while its exact target remains.

## CLI contract

Understanding modes:

```text
astra project understand <PROJECT> [--json]
astra project understand <PROJECT> --base [--json]
astra project understand <PROJECT> --explain [--json]
astra project understand <PROJECT> --require-resolved [--json]
```

`--base` cannot be combined with `--explain` or `--require-resolved`.

Inspection:

```text
astra project responses list <PROJECT> [--json]
astra project responses show <PROJECT> <RESPONSE> [--json]
astra project responses history <PROJECT> [--json]
```

Creation:

```text
astra project annotate <PROJECT> <TARGET> --statement <TEXT> --intent <INTENT>
astra project insight accept <PROJECT> <INSIGHT>
astra project insight reject <PROJECT> <INSIGHT> --reason <TEXT>
astra project insight correct <PROJECT> <INSIGHT> --statement <TEXT> --intent <INTENT>
astra project insight dispute <PROJECT> <INSIGHT> --reason <TEXT>
```

Draft and lifecycle:

```text
astra project response edit <PROJECT> <RESPONSE> [OPTIONS]
astra project response preview <PROJECT> <RESPONSE> [--json]
astra project response delete <PROJECT> <RESPONSE>
astra project response activate <PROJECT> <RESPONSE> [--supersedes <RESPONSE>]
astra project response retire <PROJECT> <RESPONSE>
astra project response withdraw <PROJECT> <RESPONSE>
astra project response reaffirm <PROJECT> <RESPONSE>
```

Selectors accept full stable target IDs or a unique friendly rule ID such as
`PI-006`. Resolution prints the full target ID and fingerprint before writing
authority. Missing and ambiguous selectors are errors.

## Tests

Unit tests cover typed payload validation, stable identities, project-scoped
sequence IDs, transaction commits and recovery, immutable history, draft
editing/deletion, lifecycle transitions, supersession, target binding,
state-bound expiration, derived-only corrections, disputes, base preservation,
resolved and explanation output, canonical ordering, and sensitive-data
rejection.

CLI integration tests use isolated configuration, projects, and
`ASTRA_KNOWLEDGE_DIR` stores. They cover every command family, selectors,
invalid option combinations, deterministic JSON, no project execution, and
base/resolved separation.

## Non-goals

- Observation challenges or suppression
- Authentication, teams, services, or multi-user synchronization
- Planning, recommendations, orchestration, or autonomous execution
- LLMs, embeddings, semantic search, or a graph database
- Dashboard integration
- Milestone 13.2 authority policy

## Definition of done

- Base Milestone 13 output remains available and unchanged under `--base`.
- Resolved output applies only active, valid operator authority.
- History and evidence remain intact across edits and transitions.
- Uncommitted transactions never affect resolution.
- All tests and workspace validation pass.
- Manual proof demonstrates acceptance expiration, correction activation,
  unchanged base output, explanation history, and deterministic JSON.
